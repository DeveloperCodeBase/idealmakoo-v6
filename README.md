## ۱. اجرای سریع

### پیش‌نیازها

- **Node.js 24 یا جدیدتر** و npm؛ بارگذار تست‌ها از قابلیت‌های داخلی Node 24 استفاده می‌کند.
- مرورگر به‌روز برای اجرای رابط. تجربه سه‌بعدی از WebGL استفاده می‌کند و برای نبود آن نمای جایگزین دارد.

دستورها را در ریشه همین مخزن اجرا کنید:

```bash
npm ci
cp .env.example .env.local
npm run dev
```

سپس [http://localhost:3000/fa/](http://localhost:3000/fa/) را باز کنید. ورود آزمایشی در [http://localhost:3000/fa/auth/login/](http://localhost:3000/fa/auth/login/) قرار دارد.

### ساخت و اجرای خروجی نهایی فرانت‌اند

```bash
npm run build
npm start
```

پیکربندی Next.js از `output: 'export'` استفاده می‌کند؛ فایل‌های قابل میزبانی در پوشه `out/` ساخته می‌شوند. دستور `npm start` اسکریپت `scripts/serve.mjs` را برای سرو همین خروجی و درگاه Google AI اجرا می‌کند و متغیرهای سروری را از `.env.local` می‌خواند. آدرس پیش‌فرض آن [http://127.0.0.1:3000/fa/](http://127.0.0.1:3000/fa/) است؛ مقدار پیش‌فرض `HOST` برابر `127.0.0.1` و `PORT` برابر `3000` است. بدون ساخت `out/`، این دستور اجرا را با پیام راهنما متوقف می‌کند.

در صورت نیاز به شنیدن روی همه رابط‌های شبکه:

```bash
HOST=0.0.0.0 npm start
```

برای انتخاب پورت دیگر، `PORT=3001 npm start` را اجرا کنید. سرور، `GET` و `HEAD`، نوع محتوای فایل‌ها، صفحه ۴۰۴ و سیاست کش فایل‌های خروجی را مدیریت می‌کند. مسیرهای حساب، ورود، مدیریت و API با `Cache-Control: no-store` ارائه می‌شوند. برای میزبانی خروجی روی سرور دیگر، این سیاست‌ها و مسیرهای دارای اسلش پایانی را در پیکربندی آن سرور حفظ کنید.

برای اتصال AI در اجرای محلی، مقدار `GOOGLE_AI_API_KEY` را فقط در `.env.local` قرار دهید و `npm run build && npm start` را اجرا کنید. `npm run dev` پیش‌نمایش توسعهٔ Next برای رابط است؛ API سروری همراه `npm start` و نسخهٔ میزبانی‌شده اجرا می‌شود. برای تغییرات کد یا متغیرهای عمومی، بیلد را دوباره اجرا کنید. کلید در سورس، ZIP و خروجی مرورگر قرار نمی‌گیرد.

## ۲. تنظیمات محیط

فایل [.env.example](.env.example) نام تنظیمات عمومی و سروری را مشخص می‌کند؛ مقادیر محرمانه در آن وجود ندارند.

| متغیر | مقدار پیش‌فرض | کاربرد |
| --- | --- | --- |
| `NEXT_PUBLIC_DATA_MODE` | `local` | اجرای مستقل با داده‌های همین مرورگر؛ مقدار `api` مرز HTTP موجود برای ایجاد درخواست را فعال می‌کند. |
| `NEXT_PUBLIC_API_BASE_URL` | `/api/v1` | پیشوند آدرس API در `HttpClient`. |
| `NEXT_PUBLIC_SITE_URL` | آدرس استقرار این نسخه | آدرس پایه وب‌سایت برای متادیتا و خروجی‌های مرتبط. |
| `GOOGLE_AI_API_KEY` | خالی | کلید Google AI؛ فقط سرور. |
| `GOOGLE_AI_TEXT_MODEL` | `gemini-3.5-flash-lite` | مدل متن و گفتگو. |
| `GOOGLE_AI_IMAGE_MODEL` | `gemini-nano-banana-2.1` | مدل ساخت/ویرایش تصویر؛ نیازمند سهمیهٔ فعال تصویر. |

برای بررسی اولیه، حالت `local` را نگه دارید. **تغییر مقدار به `api` تمام برنامه را به بک‌اند متصل نمی‌کند.** مخزن درخواست‌ها، مرز HTTP و مدل‌های TypeScript تعریف شده‌اند، اما اتصال کامل حساب‌ها، فهرست و ویرایش درخواست‌ها، CMS، CRM، رسانه و اعلان‌ها باید در مرحله بک‌اند تکمیل شود.

متغیرهای `NEXT_PUBLIC_*` در خروجی مرورگر قابل مشاهده‌اند. کلید سرویس‌های مدل، ایمیل، پیامک یا هر اعتبار محرمانه باید فقط در سرور نگهداری شود؛ درگاه Google AI همین الگو را اجرا می‌کند.

### نصب PWA و محدوده کش

صفحه `/{locale}/install/` راهنمای نصب برای دسکتاپ، Android و iOS/iPadOS دارد و اگر مرورگر رویداد نصب را در اختیار برنامه بگذارد، دکمه نصب را نمایش می‌دهد. manifest هر زبان، زبان و جهت و مسیر شروع همان زبان را مشخص می‌کند. برای ارزیابی نسخه ساخته‌شده، `npm run build` و سپس `npm start` را اجرا کنید؛ پشتیبانی و نحوه نمایش نصب به مرورگر و محیط HTTPS یا localhost وابسته است.

Service Worker فقط منابع تصویری عمومی در `public/media/official/` و فونت‌ها را، با دریافت اجازه صریح `X-Public-Cache: 1` از سرور، برای استفاده مجدد نگه می‌دارد. درخواست‌های دارای مجوز، درخواست‌های بازه‌ای فایل و پاسخ‌های خصوصی یا `no-store` وارد این کش نمی‌شوند. سرور استاتیک همراه پروژه این هدر را برای منابع عمومی مربوط اضافه می‌کند؛ میزبان دیگر باید همین سیاست را تنظیم کند.

**نصب برنامه به معنی آفلاین‌شدن همه صفحه‌ها نیست.** HTML، داده حساب، درخواست‌ها، پیشنهادهای فروش و API در کش Service Worker نگهداری نمی‌شوند. ورود، پورتال و میزکار به اتصال برای دریافت صفحه و کد برنامه نیاز دارند؛ داده نمایشی مرورگر همچنان همان محدوده محلی خود را دارد.

## ۵. سناریوی بررسی استعلام، حساب مشتری و CRM

این سناریو را در **همان مرورگر و همان آدرس وب‌سایت** انجام دهید. داده‌های دمو به مرورگر فعلی وابسته‌اند؛ مرورگر دیگر یا آدرس دیگر، پایگاه داده مشترک ندارد. برای تغییر نقش از حساب خارج شوید و با حساب مرحله بعد وارد شوید.

1. با حساب `customer` وارد شوید و به `/fa/products/` بروید. یک محصول کارخانه را باز کنید و آن را به فهرست استعلام اضافه کنید. تعداد را تغییر دهید؛ برای دندان‌ها، در صورت نیاز کد رنگ و قالب درخواستی را ثبت کنید.
2. در `/fa/inquiry-list/`، ردیف‌ها را بررسی کنید. فرم را با مشخصات همان حساب مشتری تکمیل کنید، پیش‌نمایش را ببینید و درخواست را ثبت کنید. شناسه رهگیری نمایش داده می‌شود.
3. لینک پیگیری را باز کنید. درخواست باید در `/fa/account/requests/` دیده شود و جزئیات، محصولات و پیام ثبت‌شده در دسترس باشند. همان شناسه را برای ادامه نگه دارید.
4. با حساب `business` وارد شوید و `/fa/admin/crm/leads/` را باز کنید. استعلام وب‌سایت به پرونده مرتبط تبدیل می‌شود؛ ورود دوباره به میزکار نباید از همان درخواست پرونده تکراری بسازد.
5. پرونده را باز کنید. یک یادداشت داخلی و یک پاسخ عمومی جداگانه ثبت کنید. وضعیت پرونده مرتبط را تغییر دهید. در صورت نیاز، تبدیل سرنخ به فرصت را آزمایش کنید؛ فرصت به سرنخ متصل می‌ماند و تبدیل تکراری محدود می‌شود.
6. دوباره با حساب `customer` وارد شوید و همان درخواست را باز کنید. پاسخ عمومی و وضعیت قابل مشاهده‌اند؛ یادداشت داخلی در گفتگو یا خروجی مشتری نمایش داده نمی‌شود. پاسخ مشتری را ثبت کنید و سپس آن را در پرونده CRM بررسی کنید.
7. برای کنترل مالکیت، درخواست یک حساب دیگر نباید در پورتال شخصی ظاهر شود. درخواست مهمان فقط در نمای مهمان همان مرورگر یا با تطبیق دقیق ایمیل حساب مرتبط قابل مشاهده است. داشتن نقش کارکنان، دسترسی همگانی به درخواست‌ها در **پورتال شخصی** ایجاد نمی‌کند.

کد رنگ و قالب واردشده، انتخاب درخواستی کاربر است؛ وجود آن در سبد به معنی تأیید موجودی یا سازگاری بالینی نیست. ماتریس از کدهای مستند موجود استفاده می‌کند و رنگ‌های درخواستی را کاربر وارد می‌کند. اعتبارسنجی تجاری نهایی باید به داده معتبر بک‌اند متصل شود.

### بررسی پیش‌فاکتور محلی

1. در `/fa/admin/crm/quotes/` با حساب فروش، پیشنهاد را بسازید؛ درخواست مشتری را انتخاب کنید و ارز و شرح را برای سناریوی آزمایشی وارد کنید. ویرایشگر چندردیفی امکان انتخاب محصولات واقعی، واحد، تعداد، قیمت واحد و درصد تخفیف را دارد. جمع مبلغ و تخفیف با حساب ده‌دهی و سیاست گردکردن مشخص محاسبه می‌شود؛ قیمت خالی «نامشخص» می‌ماند و پیشنهاد دارای قیمت نامشخص قابل اشتراک نیست. قیمت مرجع کارخانه در برنامه جعل نشده است.
2. پیشنهاد را برای بازبینی بفرستید. با حساب `admin` وارد همان بخش شوید و آن را با نقشی متفاوت از نویسنده تأیید کنید.
3. نسخه تأییدشده و دارای مبلغ و درخواست مرتبط را با دکمه «اشتراک نسخه مصوب در پورتال مشتری» به پورتال همان درخواست اضافه کنید. پیش از اشتراک، ردیف‌های چندمحصولی دوباره محاسبه و با جمع ثبت‌شده مقایسه می‌شوند. مشتری، ردیف‌ها، تخفیف و خالص هر ردیف و شرح نسخه را در پیشنهاد می‌بیند و می‌تواند آن را چاپ کند.
4. مشتری می‌تواند پیش از پایان اعتبار نسخه، اعلام تمایل، عدم پذیرش یا درخواست اصلاح را همراه با توضیح ثبت کند. با پایان مهلت، دکمه‌های پاسخ غیرفعال می‌شوند و ثبت پاسخ نیز در منطق برنامه رد می‌شود؛ دریافت نسخه تازه از گفتگوی درخواست قابل پیگیری است. پاسخ به سابقه پرونده فروش برمی‌گردد؛ این عمل پرداخت یا سفارش قطعی ایجاد نمی‌کند و مرحله فرصت را خودکار تغییر نمی‌دهد.

هش نسخه پیشنهاد برای شناسایی محتوای همان نسخه محلی است؛ امضای دیجیتال سروری یا سند تعهدآور ایجاد نمی‌کند.

## ۶. سناریوی محتوا: پیش‌نویس ← بازبینی مستقل ← انتشار

صفحه‌ساز نمونه مناسبی برای بررسی کامل این جریان است:

1. با حساب `contentEditor` وارد `/fa/admin/pages/` شوید. یک صفحه با عنوان و slug آزمایشی بسازید. از پالت بلوک‌ها، بخش‌های مورد نیاز مانند هیرو، متن، محصول، کاتالوگ یا خبر را اضافه کنید.
2. ترتیب بلوک‌ها، متن و پیوندها را تغییر دهید و پیش‌نمایش دسکتاپ و موبایل را بررسی کنید. «ذخیره پیش‌نویس» و سپس «ارسال برای بازبینی» را بزنید.
3. با حساب `scientificReviewer` وارد `/fa/admin/reviews/` شوید. صفحه در صف بازبینی قرار می‌گیرد. آن را با نقش بازبین تأیید کنید. تأیید توسط همان نقش نویسنده در رابط رد می‌شود.
4. با حساب `publisher` وارد `/fa/admin/pages/` شوید، صفحه تأییدشده و زبان مربوط را انتخاب کنید و «انتشار» را بزنید.
5. از لینک «مشاهده سایت» صفحه منتشرشده را باز کنید. نسخه از مسیر `/fa/page/?id=...` و فهرست `/fa/published/` قابل بررسی است.
6. یک تغییر دیگر ایجاد کنید. تغییر، پیش‌نویس جدید می‌سازد و نیاز به بازبینی دوباره دارد. نسخه عمومی بر اساس آخرین انتشار باقی می‌ماند تا نسخه تازه منتشر شود.

همین الگوی وضعیت برای محتوای محصول، پژوهش و مجموعه‌های محتوایی میزکار استفاده می‌شود. ترجمه هر زبان باید عنوان و متن خودش را داشته باشد؛ تغییر ترجمه به پیش‌نویس برمی‌گردد و انتشار زبان انتخاب‌شده، جایگزین انتشار سایر زبان‌ها نمی‌شود.

**انتشار در این نسخه محلی است:** خروجی در نمای عمومی همان مرورگر اعمال می‌شود. انتشار برای همه بازدیدکنندگان، ذخیره نسخه روی سرور، مدیریت تعارض چند کاربر و اجرای خودکار زمان‌بندی به بک‌اند نیاز دارد. تقویم فعلی زمان و وضعیت را ثبت می‌کند؛ سرویس زمان‌بندی سروری در این مخزن وجود ندارد.

### ویرایش و انتشار مشخصات محصول

در `/fa/admin/products/` محصول را در ویرایشگر اختصاصی انتخاب کنید. متن و SEO پنج‌زبانه، جنس، فیلدهای فنی، مشخصات عددی/متنی، جدول SKU و شید/قالب، گالری، منابع دانلود و provenance قابل ویرایش‌اند. ذخیرهٔ خودکار در `details.productDraft` انجام می‌شود. «ارسال برای بازبینی» نسخهٔ مستقلی در `details.productReviewDraft` می‌سازد؛ ویرایش بعدی، نسخه‌ای را که بازبین می‌بیند تغییر نمی‌دهد. بازبین می‌تواند نسخهٔ فنی را در جزئیات پرونده مشاهده و تأیید کند. ناشر پس از تأیید، آن را برای زبان انتخاب‌شده منتشر می‌کند؛ کارت، گالری اصلی، جنس، مشخصات، منابع و جزئیات محصول از نسخهٔ بازبینی‌شدهٔ منتشرشده استفاده می‌کنند؛ اطلاعات اولیهٔ مرجع در بخش جداگانهٔ منبع قابل بررسی است.

گونه‌های جدید در ابتدا وجود ندارند و تنها با ورود کاربر ساخته می‌شوند. نمایش محلی آن‌ها به معنی تأیید کارخانه یا اعلام موجودی نیست. خروجی JSON پیش‌نویس همیشه قابل دریافت است؛ خروجی `ProductEntity` پیش از تولید، انتخاب صریح taxonomy و lifecycle لازم را کنترل می‌کند. مقدار عددی نامشخص `null` است و با صفر جایگزین نمی‌شود.

### فرم سفارشی در صفحه منتشرشده

1. در `/fa/admin/forms/` فرم کارخانه را بسازید یا ویرایش کنید. فیلدهای متن، ایمیل، متن بلند، فهرست انتخاب و تاریخ، برچسب پنج‌زبانه، الزامی‌بودن و نمایش وابسته به پرشدن فیلد قبلی در دسترس‌اند.
2. در صفحه‌ساز، بلوک «فرم» اضافه کنید و فرم مورد نظر را از بازرس بلوک انتخاب کنید. بدون انتخاب فرم سفارشی، فرم تماس استاندارد نمایش داده می‌شود.
3. صفحه را ذخیره و برای بازبینی بفرستید. تعریف فرم و شماره نسخه‌اش داخل نسخه صفحه ثبت می‌شود؛ تأیید و انتشار از همان تعریف بازبینی‌شده استفاده می‌کند. تغییر بعدی فرم، نسخه عمومی قبلی را خودکار تغییر نمی‌دهد؛ برای نمایش تغییر، صفحه را دوباره ذخیره، بازبینی و منتشر کنید.
4. در صفحه عمومی، مشخصات تماس، فیلدها و رضایت پردازش درخواست را تکمیل کنید. فیلدهای پنهان‌شده به پاسخ ارسالی افزوده نمی‌شوند. ارسال موفق، شناسه رهگیری و خروجی JSON می‌دهد و درخواست در پورتال شخص مربوط قابل بررسی است.
5. در میزکار، درخواست در صندوق CRM و پاسخ در بخش فرم مربوط ظاهر می‌شود. شماره نسخه و مقادیر فرم نیز روی درخواست نگهداری می‌شوند؛ انتقال پاسخ عمومی و پیام داخلی از همان قواعد سایر درخواست‌ها پیروی می‌کند.

تعریف منتشرشده شامل پاسخ‌های جمع‌آوری‌شده نیست. اعتبارسنجی دوباره فرم، رضایت، مالکیت، نرخ ارسال و ذخیره مشترک پاسخ‌ها به بک‌اند آینده متصل می‌شوند.

### منو، فوتر و هویت مشترک

در `/fa/admin/menus/`، گروه‌ها و پیوندهای ناوبری و فوتر را اضافه، حذف، جابه‌جا یا پنهان کنید. انتخابگر زبان محتوا برای عنوان هر پنج زبان است. مسیر باید از صفحات عمومی تعریف‌شده پروژه باشد؛ پیشوند زبان هنگام نمایش ساخته می‌شود و مسیر صفحه‌ساز مانند `page?id=PAGE-...` نیز قابل انتخاب است. کنترل‌های ثابت ورود، استعلام، زبان و تم مستقل از این منوهای قابل ویرایش باقی می‌مانند.

در `/fa/admin/settings/`، نام برند، لوگوی تصویری، متن کوتاه معرفی، نشانی، تلفن و ایمیل اختیاری را برای پیش‌نمایش ویرایش کنید. بارگذاری لوگوی PNG/JPEG/WebP تا ۵۱۲ کیلوبایت و انتخاب رسانهٔ موجود در دسترس است. داده اولیه نام، نشانی و تلفن از اطلاعات کارخانه است و ایمیل این بخش در حالت اولیه خالی است. پیوند منبع اطلاعات اولیه کنار ویرایشگر قرار دارد.

«ذخیره پیش‌نویس» نسخه عمومی را تغییر نمی‌دهد. «اعمال در پیش‌نمایش سایت» ناوبری دسکتاپ و موبایل، برند مشترک و فوتر را در همان مرورگر به‌روز می‌کند؛ تب دیگری از همان آدرس هم تغییر را دریافت می‌کند. اعمال منوها، نام و تماس را تغییر نمی‌دهد و اعمال تنظیمات برند، منوهای منتشرشده را حفظ می‌کند. بازگردانی اطلاعات مرجع، بازگشت به نسخه اعمال‌شده و خروجی JSON نیز در دسترس‌اند. برای انتشار مشترک میان کاربران، همین مدل به سرویس تنظیمات بک‌اند متصل می‌شود.

### استودیو محتوا و رسانه

استودیو `/fa/admin/ai/` انتخاب محصول، زبان، مخاطب، لحن، دستور، متن قابل ویرایش، تاریخچه و ذخیره در چرخهٔ بازبینی محتوا را فراهم می‌کند. تولید متن، بازنویسی، ترجمه و سند از API واقعی Google استفاده می‌کنند. حالت تصویر، فایل تصویری واقعی سرویس را دریافت می‌کند و برای ویرایش می‌تواند تصویر مرجع معتبر دریافت کند. تصویر پس از موفقیت روی سرور ذخیره می‌شود و با مجوز مناسب به رسانه‌ها اضافه می‌شود. حالت‌های ویدئو و صوت صریحاً **سناریو و متن گویندگی** تولید می‌کنند؛ تولید فایل ویدئو/صوت در این تحویل ادعا نشده است.

درخواست قابل توقف است؛ خطاهای شبکه، کلید، سهمیه و خروجی نامعتبر به پیام مشخص تبدیل می‌شوند. نتیجه‌ای که پس از تغییر حساب یا نقش برسد ذخیره نمی‌شود. متن و تصویر تأییدنشده خودکار منتشر نمی‌شوند. چت‌بات عمومی هم چندمرحله‌ای است و منابع پاسخ، توقف، کپی و گفتگوی تازه دارد؛ سؤال‌های عمومی نیز به مدل ارسال می‌شوند.

در آزمون ۲۰۲۶-۱۰-۱۷، متن پاسخ HTTP 200 داد. مدل تصویر اصلی و مدل سبک‌تر هر دو برای کلید ارائه‌شده HTTP 429 با خطای سهمیهٔ Free Tier دادند؛ بنابراین دریافت تصویر واقعی با این حساب تأیید نشده است. بعد از فعال‌شدن سهمیه در حساب Google، همان مسیر پیاده‌شده قابل استفاده است. جای خالی تصویر با تصویر ساختگی پر نمی‌شود.

| `tests/` | تست‌های رفتاری مستقل حساب، کاتالوگ، میزکار، محاسبات تجاری، فرم، منو و سیاست کش |
| `docs/` | برنامه پیاده‌سازی، منابع، قرارداد بک‌اند، پوشش و منشأ طراحی |

متن رابط جدید را در واژه‌نامه مناسب هر پنج زبان اضافه کنید. زبان و جهت را از provider بگیرید و از پراکنده‌کردن مقادیر ثابت فارسی یا انگلیسی در کامپوننت‌های مشترک پرهیز کنید. رنگ‌ها و سطح‌های شیشه‌ای باید از تم مشترک و CSSهای همان بخش تبعیت کنند.

### تجربه سه‌بعدی و نمونه‌های ارسالی

هیروی دو دندان و آب تعاملی، مکعب شیشه‌ای و ماسکات ورود، از الگوریتم‌های واقعی نمونه‌های ارسالی اقتباس شده‌اند. مدل دندان یک تصویر ثابت نیست. موتور Three.js پشت پوشش React قرار دارد تا بارگذاری، تغییر اندازه، تعامل، تم و آزادسازی منابع با چرخه عمر صفحه هماهنگ باشند.

```tsx
<ToothExperience variant="hero" theme={theme} locale={locale} />

<ToothExperience
  variant="auth"
  theme={theme}
  locale={locale}
  privacy={passwordFocused && !showPassword}
  authMode="login"
/>

<RubikExperience theme={theme} locale={locale} />
```

موتورهای منتقل‌شدهٔ `tooth.ts`، `rubik.ts` و `auth.ts` بخشی از کد اصلی را با `@ts-nocheck` نگه داشته‌اند. ماژول‌های جدید هیرو، آناتومی، اقیانوس، دینامیک، محیط و زمان و همچنین رابط‌های React و مرزهای تعامل تایپ شده‌اند. نوع‌های جدید، کد هندسهٔ منتقل‌شده را به‌عنوان اسکن یا مشخصات تولید کارخانه معرفی نمی‌کنند.

بارگذاری نزدیک viewport، توقف در حالت پنهان، رعایت کاهش حرکت و نمای جایگزین WebGL در پوشش‌ها مدیریت می‌شوند. حرکت پوشاندن چشم‌های ماسکات فقط رفتار بصری است و مسئولیت امنیت رمز عبور ندارد. نگاشت دقیق منابع در [docs/EXPERIENCE-PROVENANCE.md](docs/EXPERIENCE-PROVENANCE.md) ثبت شده است.

## ۸. مرز فرانت‌اند و بک‌اند آینده

| موضوع | رفتار فعلی | مسئولیت بک‌اند |
| --- | --- | --- |
| حساب و نقش | نشست و کنترل نمایشی نقش در مرورگر، حساب‌های دمو و ثبت‌نام محلی | احراز هویت، MFA واقعی، مدیریت نشست، کنترل دسترسی هر درخواست و جلوگیری از دسترسی میان مشتریان |
| استعلام | فرم، اعتبارسنجی، پیش‌نمایش، شناسه محلی، گفتگو و ارتباط با CRM | ذخیره پایدار، بررسی مالکیت، اعتبارسنجی مجدد، idempotency و هم‌زمانی نسخه‌ها |
| فایل | انتخاب و نگهداری محلی فایل در مرورگر | آپلود، کنترل نوع و اندازه، بررسی فایل، مجوز دانلود و ذخیره پایدار |
| محتوا | پیش‌نویس، بازبینی مستقل در رابط، نسخه و انتشار محلی | کنترل نویسنده و بازبین با شناسه واقعی، تاریخچه معتبر، انتشار مشترک و زمان‌بندی |
| CRM و پیشنهاد | پرونده‌ها، مراحل، یادداشت، نسخه پیشنهاد و پاسخ مشتری | قواعد تجاری، قیمت معتبر، مالکیت سازمان، دسترسی رکورد، قرارداد و سفارش در صورت نیاز |
| اعلان و ارتباط | اعلان درون رابط و ثبت ترجیحات یا درخواست محلی | ارسال ایمیل/پیامک، وضعیت تحویل، اشتراک‌ها و پردازش پس‌زمینه |
| استودیو | اتصال واقعی Google AI، کلید سروری، متن/تصویر واقعی، تاریخچه و مسیر بازبینی محلی | سهمیهٔ فعال حساب، حسابداری مصرف و صف پایدار، کنترل نقش و اتصال انتشار مشترک |
| پایش | شمارنده‌های محلی، زمان‌بندی مرورگر و نمایش اتصال‌های تعریف‌نشده | تله‌متری واقعی سرویس‌ها، هشدار، لاگ عملیاتی و سلامت زیرساخت |

`HttpRequestRepository` در `src/lib/api.ts` امضاهای فهرست، ایجاد و ویرایش درخواست را تعریف می‌کند. ایجاد درخواست از هدر `Idempotency-Key` و ویرایش از `If-Match` برای نسخه مورد انتظار استفاده می‌کند. این قراردادها نیازمند پیاده‌سازی و اعتبارسنجی سمت سرور هستند؛ وجود هدر در کلاینت به‌تنهایی رفتار سرور را تضمین نمی‌کند.

آدرس API در تنظیمات میزکار، بخشی از داده نمایشی تنظیمات است؛ برای اتصال واقعی، مرزهای داده و provider باید به مخزن HTTP مربوط متصل شوند. هنگام توسعه بک‌اند، منطق مجوز و اعتبارسنجی مرورگر را مرجع امنیت قرار ندهید.

## ۹. آزمون و بررسی تغییرات

```bash
npm run typecheck
npm test
npm run check
npm run build
```

| دستور | هدف |
| --- | --- |
| `npm run typecheck` | بررسی TypeScript پروژه |
| `npm test` | اجرای تست‌های رفتاری با `node:test` و `assert` |
| `npm run check` | بررسی TypeScript و کنترل‌های ساختار/منابع در `scripts/verify.mjs` |
| `npm run build` | ساخت خروجی Next، سورس قابل‌دانلود و Worker سروری |

تست حساب شامل مالکیت درخواست، حذف پیام داخلی از خروجی، ورود و رد CSV نامعتبر، ادغام تنوع و سقف تعداد، نمک‌گذاری رمز، اعتبار مرحله MFA، تبدیل ارقام و مهلت پاسخ به پیشنهاد است. تست‌های کاتالوگ و میزکار، توابع مستقل مقایسه، انتشار و ارتباط درخواست‌ها با پرونده‌ها را بررسی می‌کنند. تست‌های تکمیلی، محاسبات ده‌دهی پیشنهاد، ادغام و جداسازی پرونده، ورود CSV، تعریف فرم و حذف مقادیر پنهان، مسیر و انتشار منو و سیاست محدود کش PWA را پوشش می‌دهند. تعداد آزمون‌های اجراشده و نتیجه نهایی را از خروجی `npm test` همان نسخه بخوانید.

بارگذار `tests/helpers/load-ts.mjs` ماژول واقعی `.ts` را با مسیر نسبت به ریشه مخزن وارد می‌کند؛ منطق برنامه در تست کپی نشده است:

```js
import { loadTs } from "./helpers/load-ts.mjs";

const { canViewRequest } = await loadTs(
  "src/components/account/portal-data.ts"
);
```

برای اجرای یک فایل با گزارش ریز آزمون‌ها می‌توانید از این دستور Node 24 استفاده کنید:

```bash
node --test --test-isolation=none tests/account.test.mjs
```

پس از تغییرات رابط، سناریوهای استعلام و انتشار همین راهنما را هم در تم روشن و تیره، یک زبان RTL و یک زبان LTR، نمای باریک و دسکتاپ بررسی کنید. تست‌های منطقی به‌تنهایی کیفیت بصری و تعامل واقعی مرورگر را اثبات نمی‌کنند.

## ۱۰. داده، منابع و نکات نگهداری

محصول، ویژگی، تصویر یا ادعای تازه را همراه با منبع معتبر در داده‌های کاتالوگ اضافه کنید. صفحات فاقد خبر، نماینده، فرصت شغلی، تأییدیه یا شاخص عمومی معتبر، نباید با اطلاعات واقعی‌نما پر شوند. محتوای مستند کارخانه و رکورد نمونه میزکار دو منشأ متفاوت دارند و برچسب نمونه باید حفظ شود.

مقاله‌ای که منبع آن فارسی است، با داشتن عنوان و خلاصه ترجمه‌شده به مقاله کامل ترجمه‌شده تبدیل نمی‌شود. برای انتشار متن ترجمه‌شده تازه، از چرخه ترجمه و بازبینی استفاده کنید. کاتالوگ‌ها و اسناد خارجی با پیوند منبع نگهداری شده‌اند؛ موجودبودن همیشگی فایل در وب‌سایت مرجع تحت کنترل این برنامه نیست.

داده‌های حالت محلی به همان مرورگر و origin وابسته‌اند. پاک‌شدن داده‌های سایت یا جابه‌جایی به آدرس دیگر می‌تواند آن‌ها را از دسترس خارج کند. قبل از بازنشانی میزکار، از خروجی JSON موجود در تنظیمات استفاده کنید. خروجی میزکار و خروجی درخواست مشتری محدوده یکسانی ندارند؛ پشتیبان کامل چندکاربره و بازیابی سروری باید در مرحله بک‌اند تعریف شود.

### رفع اشکال‌های رایج

| وضعیت | بررسی پیشنهادی |
| --- | --- |
| `npm start` خروجی پیدا نمی‌کند | ابتدا `npm run build` را اجرا و ساخته‌شدن `out/` را بررسی کنید. |
| خطای بارگذار تست یا TypeScript در Node | نسخه Node باید 24 یا جدیدتر باشد؛ وابستگی‌ها را با lockfile و `npm ci` نصب کنید. |
| درخواست API خطا می‌دهد | برای بررسی مستقل `NEXT_PUBLIC_DATA_MODE=local` باشد؛ در حالت API، آدرس و پاسخ سرور باید مطابق قرارداد باشد. |
| درخواست مشتری در مرورگر دیگر دیده نمی‌شود | حالت محلی پایگاه داده مشترک ندارد؛ سناریوی دمو را در همان origin و مرورگر ادامه دهید. |
| تغییر محتوا روی سایت دیده نمی‌شود | وضعیت باید پس از بازبینی به انتشار برسد؛ زبان انتشار و شناسه صفحه را بررسی کنید. |
| تأیید محتوا پذیرفته نمی‌شود | نویسنده و بازبین باید شناسهٔ حساب متفاوت داشته باشند؛ برای رکوردهای قدیمی، نقش نیز کنترل می‌شود. |
| دکمه اشتراک پیشنهاد در دسترس نیست | مبلغ، درخواست مرتبط و تأیید مستقل پیشنهاد باید ثبت شده باشند. |
| دندان سه‌بعدی نمایش داده نمی‌شود | برای نمایش نمای جایگزین، پشتیبانی WebGL را بررسی کنید. تنظیم کاهش حرکت، حرکت خودکار مدل را محدود می‌کند. |
